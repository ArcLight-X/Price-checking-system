# 评论区查价系统 — 基于 LLM 的商品价格情报工具

## 简历版（项目时间请填写本人实际开发时间）

**技术栈：TypeScript、Node.js、SQLite、豆包 Seed、Responses API、SQL、Git**

**项目介绍：** 面向电商页面价格难以反映真实优惠条件的问题，开发基于 B站视频评论与回复的商品价格情报工具。实现商品关键词搜索、热门与最新评论采集、对话组装、LLM 结构化抽取及结果校验，整理历史成交价、渠道、优惠条件与附加费用，输出可追溯的 JSONL 数据和 Markdown 报告。

- **端到端 AI 应用：** 设计“搜索采集—候选筛选—对话组装—模型抽取—程序校验—报告输出”处理流程，接入豆包 Seed Responses API，支持从商品名称自动发现相关视频并提取价格线索。
- **对话上下文与证据追踪：** 根据根评论及父回复 ID 恢复楼中楼关系，为消息分配引用编号，显式标记采集截断、缺失父节点和未知完整性，避免把局部回复误认为完整购买方案。
- **结构化输出质量控制：** 区分页面报价、用户报告成交价和额外费用，校验字段类型、枚举、原文引用及金额关系；结合目标型号规则过滤配件、后继型号及 Pro/Pro Max 等变体，不将评论价格标为当前已核实低价。
- **数据工程与性能优化：** 基于 SQLite 主键去重、UPSERT 和事务持久化评论；融合热门与最新评论提高线索覆盖，通过价格信号预筛减少无效模型调用，并采用可配置的有界异步任务池并发分析，保留平台抓取限速。
- **测试与故障排查：** 建立本地自动化回归测试与人工构造评测样例，围绕串型、费用遗漏、证据伪造、空响应和账户错误定位故障；记录模型耗时、Token 用量与验证问题，支持对已保存响应离线复核。

## 面试说明与真实性边界

- 这是 CLI 原型，不是已上线的商业服务；没有前端页面、完整商品知识库或实时电商价格核验。
- “历史成交”来自评论者自述，不等于订单真实性或当前可买性已经确认。
- 存在规则筛选误杀、模型语义误判，以及缓存评论过时的风险；结构校验通过不等于内容真实。
- 已有人工评测种子，但还没有正式测出的模型准确率、召回率或生产 SLA。
- 本次从已有 iPhone 17 结果读取到 30 次调用累计耗时 985,049 ms，中位数 36,136 ms。这是旧运行样本，不是新优化后的线上性能指标。
- 本轮新增默认 3 路模型并发和分阶段耗时统计；尚未进行同数据、同模型条件下的真实前后对照，简历不得写“提速 60%”或“查询降到 1 分钟”。
- 开发中使用 AI 编程辅助；面试时应如实说明，并能解释模块职责、具体故障和验证方式。

## 性能分析与下一步

1. **已修改：模型串行改为有界并发。** 默认 3 路，可通过 `--llm-concurrency 1` 对照串行；只改变等待方式，不减少所分析的候选数量。遇到账户错误停止派发，已发出的请求仍可能计费。
2. **已修改：阶段耗时统计。** 分别打印搜索、每视频采集、每视频分析和总耗时，避免将网络等待误认为数据库性能问题。
3. **已实施：成功抽取缓存。** 按模型和完整 Prompt 哈希缓存；输入变化时失效。仅复用成功校验的模型结果，不能宣称历史报价仍有效。`--no-cache` 可强制重新分析。
4. **待实施：采集快照缓存与刷新开关。** 避免重复展开未变化的楼中楼，但需记录抓取时间及所用配额，不能把少量旧样本当成全量缓存。
5. **部分实施：异常退出前落盘。** 致命 API 错误仍保留已完成结果；进程被强制终止时不能保证写入，逐条落盘与断点续跑仍待实现。
6. 不盲目提高 B站请求并发或缩短请求间隔；先优化模型等待，再根据阶段计时决定采集优化。

## 对照测试方法

固定同一批对话、相同模型和 Prompt，分别使用 1 路与 3 路并发，至少重复三次；记录墙钟时间、Token 总量、失败率及有效结果数。只有实际测试完成后才填写提升比例。离线模拟任务池测试只能证明并发行为，不能代表真实 API 提速。
